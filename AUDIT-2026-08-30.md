## 1. Dataset provenance

**The chain, file by file:**

| Step | File / function | Output |
|---|---|---|
| 1. Raw source | `data/gharchive/*.json.gz` — 72 hourly GH Archive dumps, **2026-05-28 → 2026-05-30** (3 days) | — |
| 2. Frame | `eval/build_frame.py:main()` — keeps `PullRequestEvent` with `action=="opened"`, drops bot logins (`is_bot()`: `[bot]` suffix + 5 hardcoded names), counts `prs_opened` and `distinct_openers` per repo | `eval/frame.json` (3.7 MB) |
| 3. Universe | `eval/sample_pool.py:load_universe()` — frame repos with `distinct_openers >= 2` (`MIN_OPENERS`) | in-memory |
| 4. Strata | `stratify()` — 4 PR-volume bands: `2-4`, `5-14`, `15-49`, `50+` | in-memory |
| 5. Draw | `draw()` — `random.Random(SEED=20260601)`, takes 8/8/8/6 = **30** | `eval/pool.json`, sha256 `f100b2209c1c…` |
| 6. Evidence capture | `scripts/capture_fixtures.py` → `LiveGitHubProvider`, query `repo:X is:pr created:<2026-06-01 sort:created-desc` (and `>=` for post) | `fixtures/pre_t/*.json`, `fixtures/post_t/*.json` |
| 7. Labels | `eval/run_labels.py` → `eval/labels/naive.py` (L0), `eval/labels/qualifying.py` (L1) | `eval/results_labels.json` |
| 8. Binary gold | `eval/harness.py:truth()` | in-memory |
| 9. Scoring | `eval/harness.py:score()` | `eval/results_eval.json` |

**Why these repos.** Two criteria, both observable at T: the repo had ≥1
human-opened PR during the 3-day archive window, and ≥2 distinct human openers.
Stratification by PR volume exists so the draw isn't swamped by one-PR repos.

**Sampling from GH Archive rather than GitHub Search is a genuinely good call**
and the reasoning in `build_frame.py`'s docstring is correct: Search reflects
*today's* state, so any pool drawn from it is pre-filtered for survivors.

**30 → 22, and the attrition is not random:**
- 3 unavailable — deleted between T and the run: `InteractorOSS/product-manager`,
  `Meats-Central/ProjectMeats`, `onehumancorp/mono` (`run_labels.py` `FileNotFoundError` branch)
- 5 ungraded — zero post-cutoff human outsider attempts, so `bucket ==
  insufficient_evidence`: `AlvarOnce/rancho`, `GregoIribarren94/Lendly-android-client`,
  `Lucent-Financial-Group/Zeta`, `Silver-Zhang/linux-cmd-helper`,
  `Sistema-de-certificacion-academica/…`
- **22 graded: 14 positive, 8 negative (64% positive)**

**Manual curation:** none in the draw. The seed and hash commit are real and the
"never edit after seeing results" rule appears to have been kept — `pool.json`
has not been touched since the pre-run commit.

**Selection bias — three real ones, in increasing severity:**

1. **The 3-day window + `MIN_OPENERS>=2` filter selects for repos that already
   had inbound outsider traffic at T.** That is the population where "viable" is
   already the prior, which is where the 64% positive rate comes from. It is not
   the population an early-career developer browses (which includes dormant,
   quiet and unknown repos).
2. **A 3-day sampling window over-selects high-churn repos**, including what look
   like PR farms and probe repos — `SecureBananaLabs/bug-bounty` (200 pre-T
   threads, 0 merged, 1000 post-T attempts, 0 merged), `google-test/signclav2-probe-repo`.
3. **The pre-cutoff evidence cap binds on 21 of 22 repos** — see §9.3, this is
   the most consequential one and it is undisclosed.

## 2. Ground-truth definition

`eval/labels/qualifying.py:score()` (L1), a 5-stage funnel over **post-T** records:

| Stage | Rule | Code |
|---|---|---|
| `attempts` | opener is not an author who had a merged PR **before** T | `established_authors()` (pre-T only) |
| `human` | opener not flagged as bot | `payload["author_is_bot"]` |
| `merged` | a `:merged` record exists | — |
| `substantive` | **not** docs-only, **not** data-only, **not** trivial (1 file ≤10 lines) | `is_substantive()` |
| `reviewed` | some non-bot, non-author left a review or comment | `engaged` map |

**Binarisation** — `eval/harness.py:truth()`, constants `MIN_MERGES, MIN_PEOPLE = 2, 2`:

```
gold[repo] = qualifying_merges >= 2 AND distinct_qualifying_contributors >= 2
```

Repos with `human == 0` go to a **third bucket** and are dropped from scoring —
correctly, and the reasoning in the docstring is sound.

**Cutoff.** `T_CUTOFF = 2026-06-01 UTC` (`src/holt/types.py`). Enforced by
`EvidenceProvider._assert_in_window()` raising `ContaminationError` on every
record in both directions. `eval/test_independence.py` enforces that
`eval/labels/` does not import `holt.agent`. **This machinery is real and works.**
The label window is T → run date ≈ 3 months.

**What the ground truth actually measures:** whether **at least two different
outsiders landed reviewed, non-trivial merges in the three months after T**.
That is aggregate repository throughput. It says nothing about whether any
*particular* person would succeed, and nothing about whether the contribution
was worth the contributor's time.

## 3. What Holt actually predicts

`Verdict ∈ {viable, not_viable, insufficient_evidence}` per repository, from
pre-cutoff evidence only.

Stripped of narrative, the prediction is:

> Did ≥2 distinct newcomers land merges in the (capped) pre-cutoff window, with
> median first response ≤168h — and is this not archived, a mirror, or a
> registry/list/portfolio/course?

The predictor and the label are **the same construct measured on adjacent time
windows**. `Signals.outsider_merged >= 2 AND distinct_outsider_authors >= 2`
(pre-T) versus `qualifying_merges >= 2 AND distinct_qualifying_contributors >= 2`
(post-T). The differences are the substantive/reviewed filters and the window.

`signals.py`'s docstring shows awareness of this — it deliberately keeps
diff-shape rules out of the agent so it doesn't agree with L1 "by construction."
That guards one dimension. The count-and-authors threshold is still structurally
the same test, so **a large share of the measured sensitivity is temporal
autocorrelation of outsider merge activity**, not judgement.

## 4. Exact features and signals used

`verdict.classify(findings, signals)` reads **exactly seven values**:

**From `Findings` (Stage A only) — `src/holt/agent/stages.py:classify()`**
- `is_archived: bool`
- `repo_kind: enum` — one of `real_software, registry, awesome_list, portfolio, course_material, docs, mirror, unclear`

**From `Signals` (pure arithmetic, no model) — `src/holt/agent/signals.py:compute()`**
- `outsider_threads`
- `outsider_merged`
- `outsider_ignored`
- `distinct_outsider_authors`
- `median_first_response_hours`

**Computed and then ignored by the verdict:**

| Output | Produced by | Used by verdict? |
|---|---|---|
| `bot_share` | `signals.compute()` | **No** |
| `total_threads` | `signals.compute()` | **No** |
| `governance_flags` (`cla_required`, `corporate_controlled`, `read_only`) | Stage A | **No** |
| `onboarding` (`substantive`/`boilerplate`/`absent`/`assumes_insider`) | **Stage B** `assess_opportunity()` | **No** |
| `outsider_posture` (`welcoming`/`mixed`/`discouraging`/`absent`) | **Stage C** `read_outcomes()` | **No** |
| `thread_outcome` × 12 (outcome + signal + verbatim quote) | **Stage C** | **No** |

All of these reach the rendered report as `Claim`s (`pipeline.py`) and the Stage E
narration prompt. **None reaches the decision.**

**Empirical confirmation.** I re-derived every verdict with all Stage B and
Stage C findings deleted, keeping only `repo_kind` + `is_archived` + `Signals`:

```
identical verdicts with Stage B+C findings removed: 22/22
```

**Thresholds** — all in `src/holt/agent/verdict.py`, module constants:

```python
NON_SOFTWARE_KINDS      = {registry, awesome_list, portfolio, course_material}
CLOSED_KINDS            = {mirror}
SLOW_RESPONSE_HOURS     = 168.0
MIN_MERGES              = 2
MIN_DISTINCT_AUTHORS    = 2
IGNORED_SHARE           = 0.7
MIN_ATTEMPTS_FOR_HOSTILE = 8
```

## 5. Exact decision logic

`src/holt/agent/verdict.py:classify()` — ordered, first match wins, no model:

```
1.  is_archived                                   -> NOT_VIABLE
2.  repo_kind == mirror                           -> NOT_VIABLE
3.  repo_kind in {registry, awesome_list,
                  portfolio, course_material}     -> NOT_VIABLE
4.  outsider_threads == 0                         -> INSUFFICIENT_EVIDENCE
5.  outsider_merged == 0
    AND outsider_ignored/outsider_threads > 0.7
    AND outsider_threads >= 8                     -> NOT_VIABLE
6.  outsider_merged >= 2
    AND distinct_outsider_authors >= 2
    AND NOT slow                                  -> VIABLE
7.  otherwise                                     -> INSUFFICIENT_EVIDENCE

where slow := median_first_response_hours is not None
              and median_first_response_hours > 168.0
```

**Three structural problems visible in rule 5 and 6:**

- **There is no rate rule.** Rule 5 requires `outsider_merged == 0`. A repository
  with 188 outsider attempts, 123 of them ignored, and 3 merges reaches rule 6
  and is called **viable** — a 1.6% merge rate. That is `NousResearch/hermes-agent`.
- **`median_first_response_hours is None` counts as fast.** A repo where *nobody
  ever replied to anything* has `None`, `slow` is `False`, and rule 6 can fire.
  That is `PerryTS/perry`: 3 threads, 2 merges, 3 authors, no responses at all → **viable**.
- **`repo_kind == "docs"` is unhandled.** It is in the Stage A enum but in neither
  `NON_SOFTWARE_KINDS` nor `CLOSED_KINDS`, so a documentation site falls through
  and is judged as software. `netwrix/docs` classified `docs` → viable.

**Model contribution, measured.** Scoring `Signals` alone with an empty `Findings`
(zero model calls) against the full pipeline:

| Configuration | MCC | balAcc | F1 | sens | spec |
|---|---|---|---|---|---|
| Signals only — **no model at all** | 0.42 | 0.62 | 0.82 | 1.00 | 0.25 |
| Full Holt (A+B+C+D+verdict) | 0.49 | 0.71 | 0.84 | 0.93 | 0.50 |

The model changes the verdict on **exactly 3 of 22 repositories** — all via a
single `registry` classification: `is-a-dev/register` ✓, `runelite/plugin-hub` ✓,
`Homebrew/homebrew-cask` ✗. Net +2 correct out of 22.

**The entire three-stage LLM pipeline reduces, measurably, to one binary feature:
"is this a registry?"**

## 6. Repository-centric or profile-centric?

**Unambiguously repository-centric. There is no user model anywhere.**

- `pipeline.analyze(repo: str, provider, model)` — inputs are a slug, an evidence
  provider and a model client
- `verdict.classify(findings, signals)` — no user parameter
- `holt analyze <repo>` — flags are `--baseline --replay --show-verification --live`
- `grep -rniE "profile|skills|persona|expertise|preference|resume|candidate"` over
  `src/ eval/ scripts/ tests/` → **zero hits** (only `--resume` the CLI flag)
- The only env reads in the whole codebase are `OPENAI_API_KEY` and `GITHUB_TOKEN`

**Answering your test directly:** given identical repository evidence, Aahil, a
Python backend engineer, a Solidity developer and any other person receive
**byte-identical verdicts**. The only source of variation is LLM nondeterminism
in Stage A, which is noise, not personalisation.

**Is it a hybrid?** Only in the weakest sense: a *fixed persona* — "a developer
who wants to contribute to open source and has a week to spend, usually early in
their career" (README) — is baked into prompt wording and threshold choices
(168h feels slow *to a newcomer*; 2 merges is a low bar *for a beginner*). That
persona is a constant in the source, not an input.

**Credit where due:** the README declares this as a deliberate non-use —
*"No personal fit or skill matching. No ground truth exists for 'will this
developer enjoy this', so it cannot enter the holdout."* That reasoning is sound
for the evaluation. Whether it is sound for the *product* is §8.

## 7. Concrete example of a prediction

### `opencollective/opencollective-frontend` — predicted VIABLE, gold NEGATIVE (false positive)

Pre-cutoff signals (`signals.compute()`):
```
outsider_threads = 11   outsider_merged = 5    outsider_ignored = 2
distinct_outsider_authors = 10    median_first_response_hours = 76.2
```
Stage A: `repo_kind = real_software`, `is_archived` absent.

Trace through `classify()`:
```
rule 1  is_archived            -> not set,       fall through
rule 2  kind == mirror         -> real_software, fall through
rule 3  kind in NON_SOFTWARE   -> real_software, fall through
rule 4  outsider_threads == 0  -> 11,            fall through
rule 5  outsider_merged == 0   -> 5,             fall through
rule 6  merged 5 >= 2  AND  authors 10 >= 2  AND  76.2 <= 168  -> VIABLE
```
Trace string: `"5 outsider merges from 10 people, median first response 76.2h"`

Post-cutoff reality (`qualifying.py` funnel): 14 attempts → **3 human** → 1 merged
→ **0 substantive** → 0 reviewed. Gold = negative.

Stage B said something about onboarding and Stage C read 12 threads and produced
a posture plus 12 quoted outcomes. **None of it entered this decision.**

### `Homebrew/homebrew-cask` — predicted NOT_VIABLE, gold POSITIVE (the only false negative)

Signals: 24 threads, 7 merged, 8 ignored, 16 authors, 2.2h median — rule 6 would
fire. But Stage A returned `repo_kind = registry`, so **rule 3 fires first** and
returns NOT_VIABLE with trace `"repo_kind=registry: merged work here is not a
software contribution"`. The label counts 11 qualifying merges from 5 people —
casks are Ruby files. This is honestly disclosed in the README as a genuine
disagreement, and it is the single case where the model actively hurts.

## 8. Does the system match the intended product goal?

**Stated goal:** avoid wasting a week on a repo that isn't worth pursuing.

**Cost asymmetry.** A false positive costs the user a week. A false negative
costs an *alternative* — and since there are millions of repos and Holt is a
filter, the opportunity cost of a false negative is close to zero. **False
positives are the expensive error, by a wide margin.**

**Current tuning is optimised in the opposite direction.**

| | value |
|---|---|
| Sensitivity | 0.93 |
| Specificity | 0.50 |
| Repos recommended | 17 of 22 |
| **Precision of a recommendation** | **13/17 = 0.76** |
| Same for "always say viable" | 14/22 = 0.64 |

**A user who follows Holt's recommendations wastes a week roughly 1 time in 4.**
Against the do-nothing strategy of trying everything (1 in 3), that is an
improvement, but a modest one — and it is not what the headline numbers
communicate.

**Are the thresholds optimised for the product or the metric?** For the metric.
The evidence is direct:

- The primary metric is **MCC**, which weights FP and FN **equally**. That is the
  right choice for defending against degenerate baselines (and the project's
  reasoning on that is genuinely good), but it is the wrong loss function for a
  product whose whole pitch is asymmetric.
- `eval/PREREGISTRATION.md` records a rule that **raised specificity 0.50 → 0.62**
  and was **rejected because MCC fell** (0.49 → 0.19). Under a product-aligned
  asymmetric cost that trade would at least have been evaluated differently. (In
  fairness the rule was genuinely bad — 5 good recommendations lost per 1 bad one
  avoided — so the *decision* was probably still right. The *criterion* was not
  the product's.)
- `harness.py:score()` collapses `INSUFFICIENT_EVIDENCE` into "not recommended."
  Holt ships a 3-valued verdict; the metric scores 2. The third value — the one
  that best serves a user trying not to waste time — earns no credit and carries
  no cost.

**So: 0.93/0.50 does not make sense for the stated goal.** For "don't waste my
week," the target should be high precision at whatever recall is achievable, with
`insufficient_evidence` as a cheap and freely-used escape hatch.

## 9. Discrepancies and risks

Ranked by how much they threaten the claims. I distinguish doc-claim / code-fact /
label-fact throughout.

### 9.1 The flagship mechanism is inert — partly disclosed

- **Docs claim:** *"Holt reads a GitHub repository the way a careful developer
  would after an afternoon in its pull request threads"* (README, line 5).
- **Code fact:** the verdict is 5 integers + 1 LLM enum. Stage C's thread reading
  is provably inert (22/22 ablation).
- **Disclosure:** `ASSESSMENT.md` §4.1 states this plainly and calls it *"the
  single largest gap between what the project claims and what it demonstrably
  does."* README line 194 also flags it. **Real credit for this.**
- **Not disclosed:** **Stage B (`onboarding`) is equally inert** and is mentioned
  nowhere — `grep -c onboarding README.md ASSESSMENT.md CHANGELOG.md` → `0 0 0`.
  Two of the three model stages are decorative, and only one is admitted.

### 9.2 The ablation is reported only in the metric the project itself calls degenerate

`ASSESSMENT.md:48` and `CHANGELOG.md:345` give the ablation in F1 (full 0.84,
without repo-kind rules 0.82, without arithmetic 0.79, neither 0.78). My
reproduction matches exactly. But the conclusion drawn is:

> *"On F1 the whole pipeline buys 0.06 over answering yes to everything. On MCC
> it buys 0.49 over 0.00."*

**The comparator is swapped between the two sentences.** On F1 it is compared
against the *ablation*; on MCC against a *constant*. The like-for-like MCC
ablation — which appears nowhere — is **0.42 (arithmetic only) → 0.49 (full
pipeline)**. The three model stages are worth **+0.07 MCC, delivered through 3
repositories.**

### 9.3 The pre-cutoff evidence cap binds almost everywhere, and the observation window varies by 217×

`scripts/capture_fixtures.py:PAGES = {PRE_T: 8, POST_T: 40}` → 8 × 25 = **200 PRs
max pre-cutoff**, sorted `created-desc`. **21 of 22 graded repos hit that cap.**

Because it is a fixed *count* over `sort:created-desc`, the calendar span Holt
actually observes varies enormously:

| Repo | pre-T PRs | span observed |
|---|---|---|
| `NixOS/nixpkgs`, `NousResearch/hermes-agent`, `SecureBananaLabs/bug-bounty`, `google-test/…`, `stablyai/orca` | 200 | **0 days** |
| `Homebrew/homebrew-cask`, `is-a-dev/register`, `vellum-ai/vellum-assistant` | 200 | 2 days |
| `space-wizards/space-station-14` | 200 | 20 days |
| `opencollective/opencollective-frontend` | 200 | 86 days |
| `tscircuit/kicad-to-circuit-json` | 117 | **217 days** |

**`MIN_MERGES = 2` is an absolute count applied to windows ranging from under a
day to seven months.** For a busy repo, "2 outsider merges" is a few hours of
traffic; for a quiet one it is most of a year. Meanwhile the *label* window is a
fixed 3 months. This is undisclosed and it directly explains the specificity
problem: high-volume repos clear an absolute threshold trivially.

Post-cutoff, most repos show exactly **500** captured PRs — the earlier cap. The
docstring says the cap was raised after *"three repositories hit the previous
cap"*, and `capture_fixtures.py` skips repos whose fixture already exists, so
only those 3 were re-captured at 1000. The binary gold is probably robust to this
(500 PRs is ample to find 2 qualifying merges), but the reported funnel numbers
are truncated.

### 9.4 The headline result is not robust to the ground-truth definition

The `reviewed` filter in `qualifying.py` is the most aggressive stage of the
funnel — `AseemPrasad/Legalassist-AI` goes 11 substantive → **0** reviewed.
Dropping it flips 3 of 22 gold labels, and all 3 are current Holt false positives:

| | current label | label without `reviewed` |
|---|---|---|
| **Holt** | MCC 0.49, spec 0.50, prec 0.76 | **MCC 0.74, spec 0.80, prec 0.94** |
| **Baseline** | MCC 0.33 | **MCC −0.01** |
| name-only probe | MCC 0.11 | MCC −0.10 |

**Holt's headline margin over the baseline (0.49 vs 0.33, "a 48% relative
improvement") swings to 0.74 vs −0.01 under an equally defensible label.** The
result is not wrong, but the *magnitude of the comparison is dominated by one
contestable filter*, and no sensitivity analysis over the label definition exists.

**Internal inconsistency.** `eval/PREREGISTRATION.md` rejected review-visibility
as a *feature* with the finding *"absence of in-thread review is not absence of
engagement… the pull request thread records the merge, not the conversation that
produced it."* That argument is correct — and it applies with equal force to the
*label*, which still requires exactly that visibility. If review visibility is
too unreliable to predict from, it is too unreliable to grade by.

### 9.5 "Single run" is stated as a limitation, but variance was measured and the maximum was published

- **Docs claim:** README, Known limitations — *"Single run. Variance across
  repeated runs is not measured."* `ASSESSMENT.md` §4.3 repeats it.
- **Fact:** `fixtures/trajectories/run1|run2|run3/` exist (uncommitted) with
  20–21 trajectories each. Scoring them:

| Run | MCC | balAcc | F1 | sens | spec |
|---|---|---|---|---|---|
| main (22 repos) | **0.49** | 0.71 | 0.84 | 0.93 | 0.50 |
| run1 (20) | 0.47 | 0.71 | 0.81 | 0.92 | 0.50 |
| run2 (21) | 0.47 | 0.71 | 0.81 | 0.92 | 0.50 |
| run3 (21) | 0.36 | 0.67 | 0.77 | 0.83 | 0.50 |

Observed MCC range **0.36–0.49**; the published headline is the **maximum**. The
runs cover slightly different repo counts so they are not perfectly comparable,
but the direction is unambiguous. This is the most serious *reporting* issue I
found — not because the number is fabricated, but because the docs assert the
variance is unknown while the data to state it sits in the working tree.

### 9.6 Statistical power

n = 22, with the model's entire contribution resting on 3 repositories. One repo
flipping moves MCC by roughly 0.07–0.10 — the same size as the full model
contribution and larger than the run-to-run spread between run1 and run3. **No
claim at this sample size distinguishes the pipeline from the arithmetic.**

### 9.7 Smaller code-level issues

- `repo_kind == "docs"` falls through as if it were software (§5).
- `median_first_response_hours is None` is treated as "fast" (§5) — `PerryTS/perry`
  is called viable on 3 threads with zero recorded responses.
- No merge-*rate* rule; rule 5 requires `outsider_merged == 0` (§5).
- `bot_share`, `total_threads`, `governance_flags` computed and unused.
- Star counts are as-of-fetch, not as-of-cutoff (disclosed; only the popularity
  diagnostic reads them).

### 9.8 What holds up well

Stated plainly, because it should not be lost in the above:

- The **holdout enforcement is real** — `_assert_in_window` fires on every record
  in both directions, and `test_independence.py` enforces the import boundary.
- The **hash-committed pool** was not edited after results.
- The **GH Archive framing decision** correctly avoids survivorship bias.
- The **name-only memorisation probe** is a genuine control and is reported
  honestly (MCC 0.11).
- The **constant-classifier rows** are published rather than hidden.
- `PREREGISTRATION.md` records a rule that **failed** and was removed, with the
  predictions that missed. That is rare and it is the strongest thing in the repo.
- 46/46 tests pass.

## 10. Recommendations, ranked by impact

**1. Pick the loss function before touching anything else.**
If the product is "don't waste my week," the metric must be asymmetric. Report
**precision-at-recommendation** as the headline (currently 0.76), keep MCC as the
anti-degeneracy guard, and re-derive thresholds against a cost model (e.g. FP = 5×
FN). Everything below depends on this decision. *Impact: highest — it is the
difference between a tuned system and one tuned for the wrong thing.*

**2. Publish the honest MCC ablation and fix the swapped comparator.**
`ASSESSMENT.md:57` and `CHANGELOG.md:355` should read: the three model stages buy
**0.42 → 0.49 MCC**, via 3 of 22 repositories. This is uncomfortable but it is far
stronger in front of anyone who checks — and they will check, because
`verdict.py` is 90 lines. *Impact: high, cost ~30 min.*

**3. Report variance and drop the "not measured" line.**
run1–3 already exist. Publish mean and range (MCC 0.36–0.49), not the max.
*Impact: high, cost ~20 min. This is the item most likely to be found by a reviewer.*

**4. Add a label-sensitivity analysis.**
Score against gold with and without the `reviewed` filter and publish both. It
makes Holt look *better* (0.49 → 0.74) while demonstrating exactly the rigour the
project is trying to claim — and it resolves the internal inconsistency in §9.4.
*Impact: high, cost ~1h.*

**5. Fix the three rule-level defects.**
Add a merge-rate condition so rule 6 cannot fire at a 1.6% merge rate; treat
`median_first_response_hours is None` as not-fast rather than fast; handle
`repo_kind == "docs"`. These target 2 of the 4 false positives directly and are
the cheapest specificity available. *Impact: high, cost ~1h — but see item 1: do
not tune the thresholds before choosing the metric.*

**6. Decide the personalisation question explicitly, as product scope.**
Right now Holt answers a repository-centric question and the README already
declares personalisation out of scope with sound reasoning. The options are:
(a) keep it repo-centric and align the pitch, or (b) add a profile layer
(declared languages/stack vs `primary_language` and merged-PR file extensions;
good-first-issue matching) scored on a **separate, non-holdout** metric. What you
cannot do is claim personalised viability while shipping (a). *Impact: high on
positioning, zero on current metrics.*

**7. Normalise the observation window.**
Either capture a fixed *calendar* window pre-cutoff instead of a fixed PR count,
or convert the thresholds to rates over the observed span. Currently `MIN_MERGES=2`
means something different for every repository. *Impact: medium-high, cost ~2h
including re-capture.*

**8. Resolve Stage B and Stage C.**
Two of three model stages are decorative and cost tokens on every run. Either make
one load-bearing (review-ratio already failed; a better candidate is
*first-time-contributor response rate* — response conditioned on author tenure,
which registries would score badly on), or collapse them into the narration call
and stop describing thread-reading as the mechanism. *Impact: medium — mostly
narrative integrity and cost.*

**9. Grow n.**
22 repos cannot support the current claims. A wider archive window (2 weeks
rather than 3 days) also reduces the high-churn skew. *Impact: medium, cost high.*

**10. Score the three-valued verdict as three-valued**, or ship two values.
*Impact: low-medium, cost ~30 min.*
